\section{Walk-throughs}
\label{sec:walkthroughs}

   \index{ALSA}
   Let's walk through the main test applications. There are two categories of
   tests: tests of the basic RtMidi-like API, and tests of the masterbus
   paradigm.

   The RtMidi API:

   \begin{itemize}
      \item apinames
      \item qmidiin
      \item cbmidiin
      \item midiclock
      \item midiout
      \item midiprobe
      \item sysextest
      \item test\_c\_api
   \end{itemize}

   The masterbus API:

   \begin{itemize}
      \item busin
      \item busout
      \item midiprobeex
      \item play
      \item smoke
   \end{itemize}

\subsection{Walk-throughs / RtMidi API}
\label{subsec:walkthroughs_rtmidi_api}

   The RtMidi API is encapsulated in the
   \texttt{rtl::rtmidi} namespace.

\subsubsection{Walk-throughs / RtMidi API / apinames}
\label{sec:walkthroughs_rtmidi_api_apinames}

   This test gets the compiled APIs (e.g. in Linux ALSA and JACK are compiled
   in) and the detected APIs (ALSA will generally always be found, but
   JACK requires the user to start it).

   The lists are \texttt{rtl::rtmidi::api\_list} items.
   \texttt{rtl::rtmidi::get\_compiled\_apis()} and
   \texttt{rtl::rtmidi::get\_detected\_apis()} fill the lists.
   \texttt{rtl::rtmidi::show\_apis()} shows the lists.

   Note that there are two names for the API: a short internal name and
   a better name for display. For example
   \texttt{web\_midi} and \texttt{Web MIDI API}.
   The functions are
   \texttt{rtl::rtmidi::api\_name()} and
   \texttt{rtl::rtmidi::api\_display\_name()}.
   Also tested is \texttt{rtl::rtmidi::api\_by\_name()} to
   look up the API via its short name.

   The C interface prepends "rtmidi\_" to those functions,
   and of course there is no namespace scope.

\subsubsection{Walk-throughs / RtMidi API / qmidiin}
\label{sec:walkthroughs_rtmidi_api_qmidiin}

   \texttt{tests/qmidiin} supports querying devices and then getting MIDI
   events via a
   \texttt{midi::message} or a
   \texttt{midi::event}, based on defining a macro in the source
   code.
   In addition, there is an option to read input from one MIDI source,
   or all MIDI sources.


   \texttt{tests/qmidiin}.  We run our debugger, set a breakpoint
   where the input object is created, and run using ALSA.

   \begin{verbatim}
      $ cgdb build/tests/qmidiin
      (gdb) r --alsa
   \end{verbatim}

   If JACK is not running, the option \texttt{-\-alsa} is not needed,
   as the library will fall back to ALSA (on Linux).
   Here is what happens:

   \begin{enumerate}
      \item \textbf{Select ALSA as the API}.
         \begin{itemize}
            \item Use the command-line to set the \texttt{-\-alsa} option.
            \item \texttt{rt\_simple\_cli()} sets the API to
               \texttt{rtl::rtmidi::api::alsa}.
            \item The \texttt{rt\_select\_input\_ports()} function
               presents a list of input ports.
            \item Retrieved the API with \texttt{rtl::rtmidi::desired\_api()}.
         \end{itemize}
      \item\textbf{Create the MIDI input proxy}.
         Pass the API to the
         \texttt{rtl::rtmidi\_in} constructor.
         The three possible parameters are:
         \begin{itemize}
            \item The API.  For \textsl{Linux}, they are
               \textsl{JACK}, \textsl{ALSA}, and,
               later, \textsl{Pipewire}. The default is "unspecified",
               which would invoke the fallback sequence that
               detects which APIs are available (currently
               JACK to ALSA).
            \item The client-name. Empty by default. For testing,
               the \texttt{--client name}.
            \item The input-queue size. Defaults to 100 MIDI messages.
         \end{itemize}
      \item\textbf{Open the selected API}.
         \texttt{rtl::rtmidi\_in::open\_midi\_api()} detects the compiled
         APIs and tries to create the desired one.
      \item\textbf{Create the actual MIDI input}.
         \texttt{rtl::midi\_alsa\_in()} with default client-name "rtl66 in".
      \item\textbf{Set ALSA data structure to defaults}.
         Initializes \texttt{rtl::midi\_alsa\_data} to useless defaults.
      \item\textbf{Set up the ALSA client}.
         The call sequence is:
         \begin{itemize}
            \item \texttt{rtl::midi\_alsa\_in::initialize()}
            \item \texttt{rtl::midi\_alsa::impl\_initialize()}
         \end{itemize}
            The ALSA sequencer handle (\texttt{snd\_seq\_t}) gets set up.
            Also called the "client" handle, not to be confused with
            "port" handles.
      \item\textbf{Set the tempo and PPQN}.
         \texttt{rtl::midi\_alsa::impl\_set\_tempo()}.
         Sets the default tempo and PPQN.
      \item \textbf{Get the number of ports}.
         The call sequence is:
         \begin{itemize}
            \item \texttt{rtmidi\_in::get\_port\_count()} calls
            \item Get the \texttt{midi\_api} pointer returned by
               \texttt{rtl::rtmidi::rt\_api\_ptr()}.
            \item Calll \texttt{midi\_alsa\_in::get\_port\_count()}
               via this pointer.
            \item \texttt{rtl::midi\_alsa::impl\_get\_port\_count()}
               for MIDI input.
            \item This function also gets the port capabilities via ALSA.
            \item Call the static function \texttt{rtl::get\_port\_info()}
               (in \texttt{midi\_alsa.cpp})
               with a port value of \texttt{-1}, which indicates "all ports".
         \end{itemize}
      \item \textbf{Open the input port}.
         The call sequence is:
         \begin{itemize}
            \item \texttt{rtl::rtmidi\_in::open\_port()}.
            \item \texttt{rtl::midi\_alsa\_in::open\_port()}.
            \item \texttt{rtl::midi\_alsa::impl\_open\_port()}.
            \item \texttt{rtl::get\_port\_info()}, this time for port 0.
         \end{itemize}
      \item \textbf{Get port information}.
         \texttt{rtl::get\_port\_info()} iterates through all input ports,
         retrieving port information (wasteful!) until it gets the 
         proper kind of port where the index of the port matches the
         desired port number.
         \texttt{}.
      \item \textbf{Create the port}.
         \texttt{rtl::rtmidi\_in::open\_port()} then gets the sender and
         receiver addresses, sets the client, the port, the capabilities, type,
         and number of channels in the port (16), and the port's name.
         (EMPTY!!!!!!)
         Optionally sets time-stamping information.
      \item \textbf{Port subscription}.
         \texttt{midi\_alsa::impl\_subscription()} is called to set up
         ALSA port subscription, a fancy way to connect ports.
   \end{enumerate}

   If ALSA were not specified, then
   \texttt{rtl::rtmidi::fallback\_api()} would be
   called to try JACK first, then ALSA.
   (Later, PipeWire might be the first choice).

\subsubsection{Walk-throughs / RtMidi API / cbmidiin}
\label{sec:walkthroughs_rtmidi_api_cbmidiin}

   \texttt{tests/cbmidiin} is like
   \texttt{tests/qmidiin}, except that it passes the
   \texttt{midi::message} to a short callback function that
   simply prints the message.
   The callback is called in
   \texttt{midi\_alsa\_handler()} and
   \texttt{jack\_process\_in()} (other APIs not ready).

\subsubsection{Walk-throughs / RtMidi API / midiclock}
\label{sec:walkthroughs_rtmidi_api_midiclock}

   \texttt{tests/midiclock} tests the emitting and reception of MIDI clock
   events. The build of this test creates two versions of the same
   application:
   \texttt{tests/midiclock\_in} and
   \texttt{tests/midiclock\_out}.
   Run \texttt{tests/midiclock\_in} first, read the instructions, pick a
   port (any port, 0 is fine), and then run
   \texttt{tests/midiclock\_out}.
   Pick the port named \textsl{rtl-xxxx:rtl66 midi in 0}, where "xxxx" is
   "alsa" or "jack",
   and observe that both console windows reflect clock activity.

\subsubsection{Walk-throughs / RtMidi API / midiout}
\label{sec:walkthroughs_rtmidi_api_midiout}

   \texttt{tests/midiout} tests sending a single tone.
   Once the desired output MIDI port is found, an
   \texttt{rtl::rtmidi\_out} object is created.
   Then a series of \texttt{midi::message} items are created and
   sent by \texttt{rtl::rtmidi\_out::send\_message()}.
   The messages sent are a program change, a quarter frame, a control
   change, and a note on, followed by a 500 ms sleep, a note off,
   etc.  The result should be one short note played.

\subsubsection{Walk-throughs / RtMidi API / midiprobe}
\label{sec:walkthroughs_rtmidi_api_midiprobe}

   \texttt{tests/midiprobe}
   simply lists the APIs supported and active,
   and the ports.
   The former uses the rtmidi classes, and
   the latter uses the masterbus class.

\subsection{Supported MIDI APIs}
\label{subsec:supported_apis}

   \textsl{Rtl66} supports the following MIDI APIs:

   \begin{itemize}
      \item PipeWire. (Planned, not yet implemented).
      \item JACK.
      \item ALSA.
      \item Windows Multi-Media.
      \item Mac OSX Core.
      \item Web MIDI.
      \item Dummy.
   \end{itemize}

   Audio APIs (derived from RtAudio) are planned.
