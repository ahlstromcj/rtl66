\section{High-Level Desciption of Rtl66}
\label{sec:rtl_high_level}

   \index{rtl}
   The \textsl{Rtl66} library refactors the \textsl{RtMidi} and
   \textsl{RtAudio} libraries, and then extends them with additional
   support for MIDI and audio operations.
   (Audio support is not at all ready at this time).
   Some additional helpful modules (e.g. for I/O threads) have also
   been created.

   Some of these items are directly copied from the \textsl{Seq66}
   project, with minor modifications (coding conventions,
   repartitioning) or additions such as \texttt{detect\_jack()}
   or \texttt{find\_midi\_api()}..

\subsection{Rtl Extras}
\label{subsec:rtl_extras}

   The "extras" are modules in the top-level directories
   \texttt{include/rtl} and \texttt{src/rtl}.
   They provide functionality common to MIDI and audio support.
   Additions to RtMidi are support for I/O threads and a
   test-helpers module.

   MIDI support resides in
   \texttt{include/rtl/midi} and \texttt{src/rtl/midi},
   and audio support resides in
   \texttt{include/rtl/audio} and \texttt{src/rtl/audio}.
   They both reside in the \texttt{rtl} namespace.
   In the subdirectory \texttt{rtl/midi} are subdirectories for
   ALSA, JACK, Windows MM, Pipewire, and more.
   Only ALSA and JACK are fully developed at this time.

   In addition, MIDI support adapted from \textsl{Seq66} resides in
   \texttt{include/midi} and \texttt{src/midi}.

\subsubsection{Rtl Build Macros}
\label{subsubsec:rtl_build_macros}

   The \texttt{include/rtl/rtl\_build\_macros.h}
   header file contains macro
   definitions for version information, code export settings,
   various features, and for the creation of the supported APIs.
   The latter are somewhat determined by the build platform (e.g.
   \textsl{Windows} versus \textsl{Linux}).

   In the future, some feature macros might be migrated to the
   \texttt{meson.options} file.

\subsubsection{Rtl rterror}
\label{subsubsec:rtl_rterror}

   The \texttt{rterror} class provides an enumeration to indicate the
   category of error (e.g. a driver error versus a warning),
   an alias for an error callback function, and some virtual message-related
   functions.

\subsubsection{Rtl api\_base}
\label{subsubsec:rtl_api_base}

   The \texttt{api\_base} class currently provides only support for
   the handling of errors and warnings.
   It provides the ability for a caller to set a callback function to
   handle errors, including a pointer to error-callback data.
   Free functions for printing messages are provided.

\subsubsection{Rtl rt\_types}
\label{subsubsec:rtl_rt_types}

   This C++ header file simply contains the following lines:

   \begin{verbatim}
      #include "rtl/midi/rt_midi_types.hpp"
      #include "rtl/audio/rt_audio_types.hpp"
   \end{verbatim}

\subsubsection{Rtl iothread}
\label{subsubsec:rtl_iothread}

   The \texttt{iothread} class supports starting an
   \texttt{std::thread} that will run a caller-supplied function object
   \index{functor}
   (also known as a \textsl{functor}).
   It also simplies launching and joining a thread.
   For an example of usage, see the \texttt{midi::player} class and
   the \texttt{play} test program.

\subsubsection{Rtl Test Helpers}
\label{subsubsec:rtl_test_helpers}

   Provides some free functions in the \texttt{rtl} namespace.
   They provides some simple functions to choose test I/O port numbers,
   show basic help text, handle options, brief sleep times,
   and some other basic settings.

   To show all options, use the \texttt{-\-help} option.
   Note that not all options are supported by all test applications.

\subsection{Rtl MIDI}
\label{subsec:rtl_midi}

   The \textsl{Rtl66} library consists of the core of \textsl{RtMidi} and
   extensions to it. The core is in the \texttt{rtl} namespace and
   subdirectory, while
   the extensions are mostly in the \texttt{midi} namespace and
   subdirectory.

\subsubsection{Rtl MIDI Base}
\label{subsubsec:rtl_midi_base}

   This section describes the classes and modules derived from the
   \textsl{RtMidi} library.
   Rather than a monolithic module, the classes have been split across
   multiple modules for easier management.
   They reside in the \texttt{rtl} namespace.

   Modules to support many MIDI protocols have been created, but
   currently only the ALSA and JACK APIs have been refactored
   and tested.

\paragraph{Rtl MIDI Base midi\_api}
\label{paragraph:rtl_midi_midi_api}

   \index{ABC}
   The \texttt{midi\_api} class is an \textsl{abstract base class}
   ("ABC") for all of the various MIDI OS-related class (ALSA, JACK,
   MacOSX Core MIDI, etc.).
   The actual API in use is selected from one of the compiled-in
   APIs, which depends on the build platform.

   The \texttt{rtmidi} class is assigned a pointer to an instantiated
   MIDI API class, and all the MIDI calls are done through this pointer.

   The functionality covered is:

   \begin{itemize}
%     \item \textsl{Current API}.
%        The selected API is stored for reuse.
      \item \textsl{Port type}.
         Indicates if the port is for input, output,
         duplex (both input and output), finder, and engine.
         \begin{itemize}
            \item \texttt{midi::port::io::input}.
               The port is for input.
            \item \texttt{midi::port::io::output}.
               The port is for output.
            \item \texttt{midi::port::io::duplex}.
               The port is for input or output.
               For JACK, this selects a special JACK process function.
            \item \texttt{midi::port::io::engine}.
               Engine is a concept whereby only one MIDI client needs to be
               created, and the ports can all use this common client.
               For JACK, this selects a special JACK process function.
               A single client has implications for performance and
               for multi-threading.
            \item \texttt{midi::port::io::dummy}.
               A non-functional "port". Might be useful for testing,
               or for flagging a lack of MIDI support..
            \item \texttt{midi::port::io::finder}.
               Finder means that no connections are to be made.
               Instead, the only task is to find a useable MIDI API.
         \end{itemize}
      \item \textsl{MIDI input data}.
         The \texttt{rtl::rtmidi\_in\_data} class provides data such as an
         input queue, an arbitrary API data buffer, input callback support, an
         input buffer, and some boolean flags.
         These handles are void pointers to API data or user data.
         The functions handling these pointers
         must assume the correct data type.
         Callers can optionally provide a callback function to handle
         MIDI input.
      \item \textsl{Master buss}.
         The \texttt{midi::masterbus}, if created, provides the common MIDI
         client data for the MIDI "engine".
         If not created, operation is much like that of the \textsl{RtMidi}
         library.
      \item \textsl{Engine connection/disconnection}.
         If a \texttt{masterbus} was created, a connection is stored as
         a void pointer, as each port will use the master's client handle
         and other data.
         Compare the RtMidi style in the test applications
         "midiout", "cbmidiin", and "qmidiin" with the master-bus style
         test applications "busout" and "busin".
      \item \textsl{Port enumeration}.
         Virtual functions are provided to find all existing MIDI ports, count
         them, and get their names.
         For JACK, one or two port aliases can also be obtained that
         are human readable.
      \item \textsl{Client activation/port-opening/closing}.
         For the individual port under the original "RtMidi" scheme,
         an API client (what we term "the engine") is made and activated
         (in JACK), the port is opened, used, and then closed.
      \item \textsl{Sending}.
         Virtual functions for various send operations are provided.
         Non-functional in this base class.
      \item \textsl{Receiving}.
         Virtual functions for polling and event-retrieval
         operations are provided.
         Non-functional in this base class.
      \item \textsl{Miscellaneous}.
         Various other features are provided.
         Unnecessary to describe them here.
   \end{itemize}

\paragraph{Rtl MIDI Base rtmidi}
\label{paragraph:rtl_midi_rtmidi}

   The \texttt{rtmidi} class is an abstract base class with non-virtual access
   functions for the \texttt{midi\_api} functions, plus some
   static functions.
   The functions to open a regular and a "virtual" port are virtual
   just so the default port name can be set correctly.

   The enumeration \texttt{rtmidi::api} reflects the APIs available
   (though some are not yet written); the pure-virtual function
   \texttt{open\_midi\_api()} is written in
   \texttt{rtmidi\_in}, \texttt{rtmidi\_out}, and \texttt{rtmidi\_engine}.

   A number of functions are non-virtual and non-static.
   They forward calls to the virtual functions of the current API object,
   accessed via \texttt{rt\_api\_ptr()}.
   The actual functions of the selected API are called through the stored
   \texttt{midi\_api} pointer, if it exists, as in the following
   implementation of \texttt{flush\_port()}:

   \begin{verbatim}
      bool rtmidi::flush_port ()
      {
         return rt_api_ptr()->flush_port();
      }
   \end{verbatim}

   Also defined are a number of static functions to gather information
   about the supported APIs and to select the API to be used for the
   run of an application.

   Note that \texttt{rtmidi} does not support the \textsl{Seq66/Rtl66}
   concept of a "master bus", though it is used in that paradigm.

\paragraph{Rtl MIDI Base rtmidi\_in}
\label{paragraph:rtl_midi_rtmidi_in}

   The \texttt{rtmidi\_in} class extends \texttt{rtmidi} to
   add functions for setting the input buffer size, setting or canceling
   the input callback function, ignoring MIDI data such as SysEx,
   and a function to get \texttt{midi::message} data.
   It relies on the base-class functions for some of the work.

   It also overrides \texttt{open\_midi\_api()} to try to open
   one of the MIDI APIs for input.

   An \texttt{rtmidi\_in} is provided as a member of \texttt{midi::bus\_in}
   and using in pass-along functions to get port information, poll for MIDI
   events, get \texttt{midi::messages}, and access the pointer to the
   MIDI API object.

   Should we reconsider and derive from, rather than contain,
   \texttt{rtmidi\_in}?

\paragraph{Rtl MIDI Base rtmidi\_out}
\label{paragraph:rtl_midi_rtmidi_out}

   It also overrides \texttt{open\_midi\_api()} to try to open
   one of the MIDI APIs for output.
   It relies on the base-class functions for some of the work.

   An \texttt{rtmidi\_out} is provided as a member of \texttt{midi::bus\_out}
   and using in pass-along functions to get port information, send bytes,
   send \texttt{midi::events},
   send` \texttt{midi::messages}, and access the pointer to the
   MIDI API object.

   Should we reconsider and derive from, rather than contain,
   \texttt{rtmidi\_out}?

\paragraph{Rtl MIDI Base rtmidi\_engine}
\label{paragraph:rtl_midi_rtmidi_engine}

   The \texttt{rtmidi\_in} class extends \texttt{rtmidi} to
   add a pointer to a \texttt{midi::masterbus}.

   It also overrides \texttt{open\_midi\_api()} to try to open
   one of the MIDI APIs as an "engine" (neither input nor output).
   If successful, then the \texttt{midi::masterbus} pointer is
   passed to the currently-selected MIDI API object.

\paragraph{Rtl MIDI Base Miscellaneous}
\label{paragraph:rtl_midi_miscellaneous}

   This section briefly describes some additional modules.

   \begin{itemize}
      \item \texttt{find\_midi\_api}.
         Provides free functions to find and try to open a MIDI API object.
         Some platforms provide multiple potential APIs and a fall-back
         API in case the caller does not specify one. For example,
         on \textsl{Linux}, JACK is the fallback API if detected, otherwise
         ALSA is the fallback API.
      \item \texttt{midi\_dummy}.
         This API is a non-functional class to be used only when necessary,
         perhaps in testing.
      \item \texttt{midi\_queue}.
         Provides a queue of \texttt{midi::message} objects.
         It is used for getting input events.
         It provides functions for push/pop of events, allocating data space,
         and retrieving events.
      \item \texttt{rtmidi\_in\_data}.
         Includes a \texttt{midi\_queue} for incoming data, plus
         callbacks, optional user-specific data, buffer size, API data, and
         other book-keeping for MIDI input events.
      \item \texttt{rt\_midi\_types}.
         Currently empty. See \texttt{rt\_types.hpp} instead.
      \item \texttt{rtmidi\_c}.
         Provides C-function wrappers for \texttt{rtmidi} functionality.
         Also provided are plain C enumerations corresponding to
         \texttt{rtl::rtmidi::api} and
         \texttt{rtl::rterror::kind}.
      \item \textsl{MIDI API directories}.
         Directories provided are:
         \texttt{alsa},
         \texttt{jack},
         \texttt{macosx},
         \texttt{pipewire},
         \texttt{webmidi}, and
         \texttt{winmm}.
         Their contents will be discussed elsewhere.
         Currently, only \texttt{alsa} and \texttt{jack} are fully implemented.
         Also, there are some newer APIs not yet represented.
   \end{itemize}

\subsubsection{Rtl MIDI Extensions}
\label{subsubsec:rtl_midi_extensions}

   They reside in the \texttt{midi} namespace.
   Let's get the tricky "buss" stuff out of the way first.

\paragraph{Rtl MIDI Ext. Bus}
\label{paragraph:rtl_midi_extensions_bus}

   The \texttt{midi::bus} class is base/mixin class for providing
   \textsl{Seq66} concepts for \texttt{midi::bus\_in} and
   \texttt{midi::bus\_out}.
   It is tied to the "master bus" paradigm where a single MIDI
   API ("engine") client is used to handled all ports, as busses.
   It provides the following concepts:

   \begin{itemize}
      \item \textsl{Master Bus}.
         Like \texttt{rtl::rtmidi\_engine}, this class hooks in a
         \texttt{midi::masterbus}.
      \item \textsl{Bus Index}.
         This value is an ordinal number starting at 0.
         In an application, MIDI busses are referred to by this number, not
         by name.
         This value, along with the values discussed below, is stored
         in a \texttt{midi::port} structure.
      \item \textsl{Client ID and Display Name}.
         The client number determined by the MIDI engine, if available.
         The display name is assembled by the \texttt{set\_name()} function.
      \item \textsl{Bus ID and Bus Name}.
         The buss number determined by the MIDI engine, if available.
         In ALSA, these two are the "client:bus" (e.g. "14:0") numbers.
         The bus name is obtained by \texttt{ports::get\_bus\_name()}.
         (Note: sometimes our documentation confuses port versus buss.)
      \item \textsl{Port Number, Port Name, and Port Alias}.
         The name is accessed by \texttt{get\_port\_name()} and the
         alias is accessed by \texttt{get\_port\_alias()} (useful
         only with JACK).
      \item \textsl{Port Type, Port Kind}.
         The type indicates if the bus is for input or output.
         The kind indicates if it is a system, virtual, or normal port.
      \item \textsl{Clock type}.
         Indicates both the port status (unavailable, disabled) and the
         sending of MIDI Clock and Start.
      \item \textsl{Mutex}.
         A recursive locking mutex that can be used in processing.
      \item \textsl{MIDI Processing Functions}.
         Provides function to activate/deactivate, start, send system exclusive,
         controlling MIDI Clock.
      \item \textsl{Other Functions}.
         There are functions to access all of the properties of the
         bus.
   \end{itemize}

%  these virtual functions to call the virtual function overrides of bus\_in
%  and bus\_out. But these functions are not written, and they require

\paragraph{Rtl MIDI Ext. Bus-In}
\label{paragraph:rtl_midi_extensions_bus_in}

   This class is derived from \texttt{midi::bus} and
   contains an \texttt{rtl::rtmidi\_in} object to implement
   getting MIDI messages from an external source.

   See \sectionref{paragraph:rtl_midi_rtmidi_in}.

\paragraph{Rtl MIDI Ext. Bus-Out}
\label{paragraph:rtl_midi_extensions_bus_out}

   This class is derived from \texttt{midi::bus} and
   contains an \texttt{rtl::rtmidi\_out} object to implement
   getting MIDI messages from an external source.

   See \sectionref{paragraph:rtl_midi_rtmidi_out}.

\paragraph{Rtl MIDI Ext. Bus Array}
\label{paragraph:rtl_midi_extensions_bus_array}

   The \texttt{midi::busarray} contains and manages an array of
   \texttt{midi::bus} objects.  Two of these objects are used by
   the master bus,
   one for input, and one for output.

   It is implemented by an internal \texttt{midi::busarray::container}
   object. It holds a vector of pointers to \texttt{midi::bus} objects.
   It provides functions to access a bus and do things with the MIDI
   port that it wraps.

   The \texttt{midi::busarray} object uses the "pimpl" paradigm
   \cite{pimpl}
   where its functions use a pointer to the "private"
   \texttt{midi::busarray::container} to do the work.
   Pimpl was used because of an issue with the dependence on the bus class.

\paragraph{Rtl MIDI Ext. Calculations Module}
\label{paragraph:rtl_midi_extensions_calculations}

   The \texttt{calculations} module provides enumerations and functions to
   centralize various calculations needed by a MIDI program.

   The enumerations provided support snapping time, generating waveforms,
   performing alterations such as quantizing,

   The functions, many of them inlined, support standard MIDI values for timing,
   PPQN, grid measurements, time-scaling, pitch and tempo calculations,
   and much more.

\paragraph{Rtl MIDI Ext. Client Info}
\label{paragraph:rtl_midi_extensions_clientinfo}

   This module contains two big items: a client defaults structure and
   a client-info class. It also defines a small
   input-specification structure.

   The \texttt{midi::client\_defaults} structure contains members to specify
   client and application name, API version, preferred MIDI API, thread and port
   usage, and more.  The application should make an instance of this structure and
   initialize it. See the "busin" test application, for example.

   The \texttt{midi::input\_specs} specifies if the input is active, uses
   SysEx, time code, active sensing, an optional user callback and optional
   data. See the "busin" test application, for example.

   The \texttt{midi::clientinfo} class contains both of those structures with
   constructors that can get those structures. The class adds
   current and previous \texttt{midi::ports}, saves a pointer to the client
   (engine) handle, status flags, and an error string.

   The client-info object is later filled with a list of the existing MIDI ports.
   Some of the items loaded into this object can potentially saved to a
   configuration file.

%  For one example, see the file \texttt{tests/midi/busin.cpp}.

\paragraph{Rtl MIDI Ext. Clocking}
\label{paragraph:rtl_midi_extensions_clocking}

   The \texttt{clocking} module contains \textsl{Seq66} concepts for
   MIDI clocking. There are enumeration values for starting/stopping MIDI
   clock, the clocking and input/output status of a MIDI port, and some functions
   to check the clocking values.

\paragraph{Rtl MIDI Ext. Event Codes}
\label{paragraph:rtl_midi_extensions_event_codes}

   The \texttt{eventcodes} module somewhat duplicates the "EVENT\_xxx"
   macros in the \texttt{seq66::event} class, but instead uses enumerations
   in the \texttt{midi} namespace, and functions to deal with them.

   The \texttt{midi::status} enumeration class defines note off, note on,
   and other statuses.

   The \texttt{midi::meta} enumeration class defines the MIDI meta events such as
   track number, time/key signatures, text events, and more.

   The \texttt{midi::ctrl} enumeration class defines the MIDI control
   events such as volume and balance.

   Many conversion functions are provided to convert between the enumeration
   values and simple data types; to determine what a byte actually means;
   to get the human-readable name for the event, RPN conversions, and more.

\paragraph{Rtl MIDI Ext. Events}
\label{paragraph:rtl_midi_extensions_events}

   The \texttt{midi::event} class is much like \texttt{seq66::event},
   but it also uses the \texttt{eventcodes} module, and is more
   "C++" than the original.
   Instead of a byte array, it holds a \texttt{midi::message}.
   See \sectionref{paragraph:rtl_midi_extensions_message}.

   It is still \textsl{not} broken into a class hierarchy of events,
   something that we worry about.

\paragraph{Rtl MIDI Ext. Event List}
\label{paragraph:rtl_midi_extensions_eventlist}

   The \texttt{midi::eventlist} class is much like \texttt{seq66::eventlist}.
   It has enumerations for selecting and editing events.
   It has many functions for editing the list, storing events,
   getting the events, iterating through events, and all of the other modifications
   supported by \textsl{Seq66}.

\paragraph{Rtl MIDI Ext. File}
\label{paragraph:rtl_midi_extensions_file}

   The \texttt{midi::file} class recreates the basic part of
   the \texttt{seq66::midifile} class.
   It deals with \texttt{midi::tracks} instead of "sequence" objects,
   but not sequencer-specific events.

\paragraph{Rtl MIDI Ext. Master Bus}
\label{paragraph:rtl_midi_extensions_master_bus}

   The \texttt{midi::masterbus} class is similar to that concept in
   \textsl{Seq66}, but does not (at this time)
   require deriving a child master bus.

   It supports having a single MIDI API client handle (an "engine")
   that is used by all of the ports in the input/output
   \texttt{midi::busarray} objects.
   It holds a void pointer to the client handle.
   It holds a clientinfo.

   Normally, using the basic "rtmidi" process requires creating
   a new client handle for each port.

   On the other hand, the \texttt{midi::masterbus} creates the
   client handle that all of the ports use, and manages the whole
   setup process. The use of a single client handle has implications
   for some of the processing.

   Examples in the \texttt{tests/midi} directory are the
   \texttt{busin},
   \texttt{busout},
   \texttt{play}
   test applications.
   In the future, we will experiment with processing such as round-robin port
   selection, to improve latency.

\paragraph{Rtl MIDI Ext. Measures}
\label{paragraph:rtl_midi_extensions_measures}

   The \texttt{midi::measures} class is a small class to manage
   beats, bars, and divisions (data type \texttt{midi::pulse}).

\paragraph{Rtl MIDI Ext. Message}
\label{paragraph:rtl_midi_extensions_message}

   The \texttt{midi::message} class contains a static counter for debugging,
   a floating-point time-stamp, a container of \texttt{midi::bytes},
   an optional channel number, an option MIDI buss index number, and
   an optional MIDI event type (an ALSA concept).

   It holds all of the bytes for a message, so saving the event or writing it
   is very simple (unless applying a channel)... just dump the bytes.

\paragraph{Rtl MIDI Ext. Midibytes}
\label{paragraph:rtl_midi_extensions_bytes}

   The \texttt{midibytes} modules is basically the same module
   copped from \textsl{Seq66}. It defines, in the "midi" namespace,
   aliases for integer, boolean, and byte types, plus a vector called
   \texttt{midi::bytes}. It defines functions to test bytes, convert to
   a pointer, clamp values to byte-size, and more.

\paragraph{Rtl MIDI Ext. Player}
\label{paragraph:rtl_midi_extensions_player}

   The \texttt{midi::player} class can read a simple MIDI file and play it.
   It accepts a reference to a \texttt{midi::masterbus}, and provides 
   an output thread. It can also poll for MIDI events.
   It's not complete, but is meant for testing and experimenting.
   It includes a nested "synch" class for managing a condition variable 
   to control output.
   It uses an output thread function.
   See the "play" test app.

\paragraph{Rtl MIDI Ext. Poller}
\label{paragraph:rtl_midi_extensions_poller}

   The \texttt{midi::poller} class, like \texttt{midi::player},
   is a provisional class for testing and experimentation, except
   that it polls for data rather than sending MIDI events.

   It includes an \texttt{xpc::fifo<midi::message>}
   (from the \textsl{xpc66} library project) and
   \texttt{std::unique\_ptr<inqueue>} to store the incoming data.
   It includes a nested "synch" class for managing a condition variable 
   to control input.
   It uses an input thread function.
   See the "busin" test app.

\paragraph{Rtl MIDI Ext. Port}
\label{paragraph:rtl_midi_extensions_port}

   The \texttt{midi::port} class is a data class that describes information about
   a port, including the system numbers and names of the port, the index of the
   port in the application, alias names (if applicable) for the port,
   the client number, whether retrieved from the system or made up, is
   the "buss" number.

   Also defined are the \texttt{midi::port::io} and
   \texttt{midi::port::kind} enumerations.
   The former indicates what the port is meant for; see
   \sectionref{paragraph:rtl_midi_midi_api}.
   The latter indicates if the port is to be a normal, manual (i.e. virtual),
   or system port.
   Also see \sectionref{paragraph:rtl_midi_extensions_clientinfo}.

\paragraph{Rtl MIDI Ext. Port Naming}
\label{paragraph:rtl_midi_extensions_port_naming}

   The \texttt{midi::portnaming} module
   is meant to extract port-naming information from system port names or
   aliases.
   The \texttt{midi::portnaming} enumeration class provides for
   styles of brief, pair, and full naming styles.
   Functions are provided to extract the client/buss name, the port
   name, names created by the \texttt{a2jmidid} daemon,
   JACK alias names, and short names called "nicknames" which are cleaner
   than full port names and can be useful in port-mapping (as in
   \textsl{Seq66}.

\paragraph{Rtl MIDI Ext. Ports}
\label{paragraph:rtl_midi_extensions_ports}

   The \texttt{midi::ports} class provides a container of
   \texttt{midi::port} objects of the same type (input, output).
   The default port type is \texttt{midi::port::io::dummy}.

   Functions are provided to add port data to the container,
   access port data by buss index, etc. Many of these functions
   simply look up the \texttt{midi::port} object and retrieve
   port data members.

\paragraph{Rtl MIDI Ext. Scales}
\label{paragraph:rtl_midi_extensions_scales}

   The \texttt{midi::scales} module provides enumeration classes
   for musical keys, musical scales, and chords.
   Functions are provided to convert between these enumeration
   values and integer values and to validate values.
   Functions are provided to get human-readable names for the
   scale, transpose the scale up or down, etc.
   These functions are useful for selecting a key, a scale,
   and a chord from a GUI element.

\paragraph{Rtl MIDI Ext. Splitter}
\label{paragraph:rtl_midi_extensions_splitter}

   The \texttt{midi::splitter} class provides a way to split
   an SMF 0 \texttt{midi::track} into a number of
   tracks on a per-channel basis.
   The resulting tracks are installed into a
   \texttt{midi::player} object.

\paragraph{Rtl MIDI Ext. Timing}
\label{paragraph:rtl_midi_extensions_timing}

   The \texttt{midi::timing} module and class holds
   information and limits about time signatures, PPQN, clocks/metronome,
   32nds/quarter, and microseconds/quarter-note.

   The most important functions related to beats/bar (BPB),
   beat width (BW), pulses per quarter-note (PPQN), and
   beats/minute (BPM).

   Also see \sectionref{paragraph:rtl_midi_extensions_track_info}.

\paragraph{Rtl MIDI Ext. Track}
\label{paragraph:rtl_midi_extensions_track}

   The \texttt{midi::track} class is a cut-down version of
   the \texttt{seq66::sequence}.
   It has an enumeration to determine how recording is to work.
   It has a pointer to its owning ("parent") \texttt{midi::player} object.
   It holds a \texttt{midi::trackinfo} object, a
   \texttt{midi::trackdata} object, an
   \texttt{xpc::recmutex}, a
   \texttt{midi::masterbus},
   and a number of attributes describing the tracks.

\paragraph{Rtl MIDI Ext. Track Data}
\label{paragraph:rtl_midi_extensions_track_data}

   The \texttt{midi::trackdata} class holds a partial set of data for
   a track. It contains a
   \texttt{midi::eventlist}, a
   \texttt{util::bytevector}, and
   some other status.
   The \texttt{util::bytevector} is a class that handles big-endian data;
   MIDI is encoded in big-endian.

   The \texttt{midi::trackdata} class provides a number
   of "get" functions to get values and parts of MIDI events from
   bytes,
   plus a number of "put" functions to convert basic data items and
   MIDI events to bytes, 
   plus a number of "extract" functions to extract MIDI
   events from the current location in track data.

\paragraph{Rtl MIDI Ext. Track Data Ex}
\label{paragraph:rtl_midi_extensions_track_data_ex}

   The \texttt{midi::trackdataex} class is smaller than
   \texttt{midi::trackdata}, and works with "triggers".
   However, it is not compiled into the build, and is a work in progress.

\paragraph{Rtl MIDI Ext. Track Info}
\label{paragraph:rtl_midi_extensions_track_info}

   The \texttt{midi::trackinfo} module provides supplemental classes
   to group data items and simplify function calls by using data
   structures.
   It defines the following classes:

   \begin{itemize}
      \item \texttt{tempoinfo}.
         The members specify a tempo track number, beats/minute, and
         microseconds/quarter-note.
         Compare it to the \texttt{midi::timing} class
         (\sectionref{paragraph:rtl_midi_extensions_timing}.
      \item \texttt{timesiginfo}.
         The members specify beats/bar, beat-width, clocks/metronome, and
         32nds/quarter-note.
         Compare it to the \texttt{midi::timing} class
         (\sectionref{paragraph:rtl_midi_extensions_timing}.
      \item \texttt{keysiginfo}.
         The members specify the name of the key-signature, the sharp/flat
         count, and a flag for a minor scale.
      \item \texttt{trackinfo}.
         Defines the track name, its length, the three classes above in this
         list, an optional channel override, an a flag for being
         exportable (to be explained elsewhere).
   \end{itemize}

\paragraph{Rtl MIDI Ext. Track List}
\label{paragraph:rtl_midi_extensions_track_list}

   The \texttt{midi::tracklist} class provides a vector of
   pointers to \texttt{midi::track} objects, plus the modified and sorted
   statuses.
